# 图片支持审计与修复

审计对象：Claude 留下的未提交 0.9.1 图片实现。结果：用户附件的原生图片传递方向正确，工具图片、缓存覆盖范围及执行配置存在缺口，已补齐为 0.9.3。

## 确认的问题

| 问题 | 影响 | 修复 |
| --- | --- | --- |
| `tool_result` 强制提取纯文本，编译器仅接受 user 图片 | 本地读图、截图工具返回图片会收到 400 | 工具图片保留原生块、调用 ID、错误状态与原始顺序 |
| 缓存断点在图片之前 | 最后一组图片不在网关显式缓存前缀内 | 每个含图消息固定追加 `image_end` 文本块，在完整前缀末尾设置断点 |
| 官方 CLI 移除 image 上的 `cache_control` | 直接改成图片断点无法兑现 | 真实 CLI 回环探针发现并验证文本结束块方案 |
| 单图上限只传到 HTTP 校验，执行层使用默认值 | 自定义上限通过入站后仍可能执行失败 | 同一 `maxImageBytes` 贯穿入站校验、执行校验和上下文编译 |
| base64 正则只检查字符集合 | 不完整补位、非规范尾位仍可能进入上游 | 校验长度、补位和末尾未使用的位；每请求最多 100 张图片 |

官方 [Messages 类型定义](https://platform.claude.com/docs/en/api/typescript/messages)允许图片块带缓存标记，但这不能证明官方 CLI 会保留该字段。CLI 2.1.277 的实际探针中图片内容被保留、图片缓存标记被移除，因此采用固定文本块承载断点。

## 验证

- Windows 本地：42 项测试通过，包括原生 HTTP 工具图片、错误状态、图片顺序、损坏 base64、100/101 张边界、自定义大图上限、请求体与在场字节额度归还。
- Linux 服务器：42 项测试通过；修复缓存承载块后另验证两条真实 CLI 路径。
- `cloud-probe.mjs --self-test --images` 与 `--self-test --images --anthropic` 均通过：首轮 1 张附件、次轮 2 张图片（历史附件 + 工具截图）；最终上游数据一致，每个图片块的数据只出现一次，正文没有 base64，5m 缓存标记到达上游，旧系统/工具/图片历史前缀保持一致。原生路径同时验证 high/low 思考档位。
- 所有上游探针连接服务器回环模拟接口，不调用真实模型，不测试图像理解能力或实际缓存命中率。

## 保留的边界

- 只接受 base64 内联 PNG/JPEG/GIF/WebP；远程 URL、助手图片、音频与文档块显式拒绝。
- 默认单图 5MiB，请求体 32MiB，同时在场的请求体总量 64MiB，3 个执行槽、8 个等待槽；超额返回 413/429。字节准入并非 RSS 保证，进程仍受 systemd 的内存限制。
- 图片不在网关解码或缩放，EXIF 原样保留；实际图片有效性及尺寸处理交给官方 CLI/上游。
- 缓存标记与前缀稳定性已经验证，实际命中仍由上游决定。
