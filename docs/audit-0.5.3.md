## 缓存证据与边界

受控测试使用同一调用方 system、同一工具定义，第二轮追加 assistant/tool 消息。两轮均启动新的官方 CLI 进程：

- 精确工具集合只有 `mcp__omp__read`。
- 两轮 system SHA-256 都是 `5c36b3498f9ee8bafa5aab03bf800abe5f0f44854458c97ade96efd3989c4c7a`。
- 两轮工具定义 SHA-256 都是 `1415a15ed137d2d3285500b88a92ff0041c426b06f534def2b74645b009aeb25`。
- 原有调用方消息块逐字保留，末尾 `cache_control: {type: ephemeral, ttl: 5m}` 确实到达上游。
- CLI 在断点之后追加一条环境消息，包含固定 cwd、系统版本、日期、模型等内容。同一次两轮验收里该消息也一致。探针分别检查缓存前缀和断点之后的内容，避免把正常追加历史误判为前缀损坏。
- 存在 metadata；它与提示词分开检查。受控提示词没有出现每轮 `request-*` 临时目录，不能由此推断所有上游元数据完全固定。

最初把整份 messages（包括 CLI 放在末尾的环境消息）都当作旧缓存前缀，会错误地让第二轮失败。现在测试比较到旧断点为止的真实前缀，并单独报告断点后的块数和哈希；没有移除或伪造官方 CLI 的身份信息。

`--bare` 会跳过 OAuth/keychain，不能为缩短提示词而直接用于本项目的订阅路线。这一限制由服务器安装版本的 `--help` 核验。环境信息仍有额外 token 开销；本轮没有改写官方程序消除它。

以上说明新进程不必然破坏提示词缓存，不代表真实缓存已经命中。每轮仍全量上传历史，缓存是否生效还受上游阈值、有效期、模型及调用方前缀变化影响；实际额度、延迟和长对话效果仍需 Pro/Max 登录后测试。模拟返回的 usage 只是测试数据。

## 验证与运行状态

- Windows 与云端 Linux：14 项自动测试通过，覆盖导入失配、事件顺序、多个工具、未完成消息、取消清理、HTTP/SSE 参数错误、精确工具集与前缀检查。
- 真实 OMP：隔离配置、合成网关、临时文件，两轮读工具往返通过。实际请求字段为 max_completion_tokens、messages、model、store、stream、stream_options、tools。
- 云端官方 CLI：隔离目录和临时端口，回环模拟上游两轮通过。没有使用 OAuth 或真实模型 API。
- 安装脚本通过 Bash 语法检查；没有在正式服务运行全套重装或防火墙变更。

正式云端服务未被此轮替换，已有 OMP 配置和 OAuth 状态未修改。仓库修复与隔离验收完成后，可在单独部署步骤更新常驻服务；真实订阅验收仍待登录。
