## P1：完整 assistant 回退不能交付工具调用

位置：[native-cli-session.mjs](../../model-gateway/native-cli-session.mjs) 的 line() 中 awaitingStart 门控；[cli-events.mjs](../../model-gateway/cli-events.mjs) 的 accept() 中 assistant 分支。

触发条件：CLI 返回完整正常 assistant，其中包含 tool_use，但本轮没有先发 stream_event/message_start，例如 PR #4 描述希望兼容的重试后非流式回退。awaitingStart 仍为 true，完整 assistant 被提前丢弃。即使仅放开这处门控，CliEvents 的完整 assistant 分支只收集工具调用，不依据完整消息结束状态设置 toolEnd，依然不会进入原生 MCP 工具交接。

影响：调用方拿不到工具请求；如果 CLI 已等待 MCP 结果，双方互相等待，最终超时或封存。普通文本如果 result 自带正文可能有兜底，不能据此推导工具路径也可用。

本地合成复现：创建 NativeCliSession 的活动 turn（awaitingStart=true），输入带 stop_reason=tool_use 的完整 assistant，验证 events.calls.size=0；同一事件直接交给 CliEvents 时 calls.size=1，但 toolEnd=false。两项断言均通过，无真实模型请求。

修复方向：识别完整正常 assistant 的有效消息边界，并让它与流式事件共用工具结束、去重和参数验证；继续排除 is_api_error_message，并保留真实 MCP 等待核验。仅删除 awaitingStart 检查不足以修复。

## P2：提高输出上限会让同一原生会话无法续接

位置：[session-relay.mjs](../../model-gateway/session-relay.mjs) 的 signature 构造和会话筛选。

触发条件：历史、模型和工具相同，客户端将 max_tokens 从 1024 提高到 2048，且两者均小于配置接受上限 8192。outputTokens 被放入精确签名，旧会话被跳过；网关转向新会话入口，又因携带旧历史被 NATIVE_RESUME_REQUIRED 拒绝。sticky 会话则可能进入不匹配封存分支。

本地合成复现：模拟 CLI 完成第一轮，追加真实返回的 assistant 与下一条 user；仅提高预算收到 NATIVE_RESUME_REQUIRED。将同一请求预算恢复为 1024 后正常返回 READY，整个过程只启动一个模拟 CLI。这证明是预算匹配导致，非历史损坏。

修复方向：区分客户端本轮允许上限与现存 CLI 的实际配置上限，明确预算提高时的复用策略；拒绝无法满足的新低上限，并覆盖存活会话、sticky 和持久检查点恢复。PR #4 文案提到的兼容策略未包含在实际补丁中。
