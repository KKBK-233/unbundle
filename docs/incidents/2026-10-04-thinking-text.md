## 后续复现与取证要点

若另行授权真实复现，应优先还原以下条件，并记录各轮关联号和生命周期：

1. 长工具会话，保留接近原现场的历史规模、工具数量和图片数量；采用合成或用户明确授权的素材。
2. High → Max、卡顿后人工取消、同会话 `Try again`；明确取消到旧 CLI 退出、旧请求清理到新请求启动的间隔。
3. 同时记录本机和云端 CLI 版本、实际模型、档位、输出上限及上下文统计。
4. 发现候选异常后允许它自然输出完，区分自然完成、主动取消和网络断开，避免再次丢失终态。
5. 对比 CLI 可见的 block/delta 类型、签名次数与长度、正文/思考通道指纹。网关观察不到上游原始 API SSE，仍需上游侧证据才能缩小定责范围。

以上是后续复现条件，**没有自动重放或新增真实请求**。当前证据不足以确认“同会话两个上游任务阻塞导致第二个未加密”这一假设。

从网关 **0.11.16** 起，[异常通道自动取证](../anomaly-capture.md)会被动保存自然请求中的候选信号，只落盘元数据，不改变档位、预算或输出。它覆盖正文 thinking 标签、块/delta 类型冲突以及正文与 thinking 通道指纹相同；普通 thinking、尚未结束时缺少签名不会单独触发。

该机制不能捕捉所有语义上的异常，也不能从 CLI 事件证明上游的加密状态。新的记录应与本事故分开保存，不以检测结果倒推本次事故的缺失证据。
